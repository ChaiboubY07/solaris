# Product Principles

These principles define how Solaris should feel and what it should avoid.

## 1. The world comes first

Solaris should feel like a place, not a dashboard.

The Solar System is the main interface.
UI elements should support exploration, not dominate it.

---

## 2. Planets are personalities, not categories

A planet must never be reduced to a topic.

Bad:
- Mars = debates
- Venus = love
- Jupiter = science

Good:
- Mars = provocative
- Venus = empathetic
- Jupiter = sociable

The topic comes from the conversation.

---

## 3. AI should feel alive

Planet AIs should have:

- personality
- opinions
- memory
- mood
- relationships

They should not behave like eight copies of the same chatbot wearing different skins.

---

## 4. Real-time must be visible

If something happens in a conversation, other users should be able to feel it.

Examples:

- messages appear instantly
- users join/leave in real time
- planet mood changes
- the environment reacts

WebSocket should have a reason to exist beyond "because we can".

---

## 5. Simple interactions, rich consequences

The user should have very few things to learn.

The complexity should live behind the scenes.

One message can trigger:

User message
→ AI response
→ mood change
→ visual reaction
→ relationship update

Simple input. Interesting result.

---

## 6. The app must work when empty

A new visitor should not need 50 other users online to have fun.

Planet AIs provide the core experience.

Other humans make it better, not functional.

---

## 7. Discovery over instructions

Whenever possible, let users discover features naturally.

Avoid:

"Step 1: Click here."

Prefer:

"Mars wants to talk to you."

---

## 9. Real astronomy, fictional personalities

The Solar System itself should remain recognizable and based on the real planets.

The fictional part is the AI personality and social world built around them.

Maybe we can find searchs on the web to get more information about the planets and their characteristics.

---

## 10. Quality matters

Every major feature should answer two questions:

1. Does it improve the user experience?
2. Does it demonstrate meaningful technical skill?

If the answer to both is "no", we probably don't need it.
